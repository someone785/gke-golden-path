> 【これは意図して起こした障害】フェーズ 2 のデモとして、OTel Demo の flagd の `paymentFailure` を `50%` にした。
> 利用者は OTel Demo の load-generator と、デモの操作をした人だけ。
> 通し稽古 ([2026-11-14](2026-11-14-payment-failure-rehearsal.md)) の対策 (時刻の記録、アラートの解消までの時間) も確かめた。

## 要約
payment の Charge が 50% の確率で失敗するようにしたところ、checkout の注文 (PlaceOrder) の失敗率が最大 69% (5 分の窓) になった。
約 2 分 20 秒で ticket のアラートが、約 6 分 20 秒で page のアラートが鳴った。
メトリクスで payment に絞り込み、Jaeger のトレースで発生源 (payment の `charge`、`Invalid token`) を特定した。
フラグを `off` に戻して約 5 分で回復した。page のアラートは約 24 分後に解消したが、ticket は 40 分たっても鳴り続けた。

## 原因
- **直接の原因**: flagd の `paymentFailure` を `50%` にしたため、payment の `charge` が半分の確率で例外 (`Invalid token`) を投げた。
- checkout は注文の処理の中で payment の Charge を呼ぶ。Charge が失敗すると注文 (PlaceOrder) 全体がエラーになり、frontend は 422 を返した。
- frontend は 422 を受けても、利用者に何も表示しない (OTel Demo の作り)。

## 検知と特定
1. **検知**: Sloth で生成した多窓のバーンレートのアラートが鳴った。先に ticket、約 4 分後に page。
2. **通知**: Alertmanager に、日本語の要約と Runbook の URL が付いて届いた。
3. **絞り込み**: Runbook の手順 3 の式で、エラーを出している span をサービスごとに並べた。checkout、frontend、frontend-proxy のほかに payment が出ていた。ただし上位 7 行は同じ値で、メトリクスだけでは発生源を決められなかった。
4. **特定**: Jaeger で失敗したトレースを開き、赤い印を呼び出し先へたどった。一番深い span は payment の `charge`。例外のメッセージとスタックトレース (`charge.js:48`) まで読めた。

## うまくいったこと
- 通し稽古と同じ流れで、検知から特定まで迷わずに進めた。Runbook の手順 3・4・5 がそのまま使えた。
- 時刻を Prometheus (`activeAt`、`query_range`)・Jaeger・Alertmanager の API から取り戻せた。手で記録しそこねた時刻も、根拠のある値で埋められた。
- 通し稽古で分かった「直ってもアラートが鳴り続ける」を Runbook に書いておいたので、慌てずに済んだ。

## うまくいかなかったこと
- **手での時刻の記録が続かなかった**。`echo` での記録は最初の 1 回だけで、途中から Claude が API から取り戻した。画面の操作と撮影で手が足りない。
- **page が鳴るまで約 6 分かかった**。障害の前に 10 分以上待ったので、1 時間の窓に平常の時間が長く含まれ、「5 分と 1 時間の窓で 14.4% 超」が成り立ちにくかった。注文が 1 分あたり約 2.7 件と少ないことも影響した。
- **ticket のアラートが解消しない**。クラスタを作って 2 時間以内は、2 時間・6 時間・1 日・3 日の窓がすべて「起動してから今まで」になり、障害中のエラーがずっと残る。作っては消す運用では、ほぼクラスタを消すまで鳴り続ける。
- 通知先が Alertmanager の画面だけなのは、通し稽古から変わっていない (フェーズ 3 で対応)。
- 解消までの時間の見込みを、page だけで見積もり、ticket の長さを見落とした (約 15 分、余計に待った)。

## 運が良かったこと
- 原因が 1 つのサービスに閉じていた。
- 障害を起こしたのが自分 (flagd) だったので、Runbook の「最初に flagd を確かめる」がそのまま当たった。
